- **Platform:** Android Native
- **Web/React:** None present. Completely native Android UI built with Compose.

## 2. Main Entry Point
- **Activity:** `MainActivity.kt`
- **Main Composable:** `ChromaProApp` (in `ChromaProApp.kt`)

## 3. Current Editor Screen File
- `ChromaProApp.kt` orchestrates the top-level panels and acts as the main editor screen for the app layout.

## 4. Current Viewport File
- `VideoViewport.kt` located in `/app/src/main/java/com/example/timeline/ui/viewport/`.

## 5. Current Timeline Files

- `TimelineRuler.kt`: The top ruler for the playhead dragging and time markers.
- `TrackHeader.kt`: The headers for adjusting track state (mute, hide, lock).

## 6. Current Color Grading Screen File
- `ProfessionalColorGradingScreen.kt` (in `com/example/ui/colorgrade/`).

## 7. Current Transform/Motion Files
- `TransformPanel.kt` (in `com/example/ui/transform/`).

## 8. Current ViewModel / State Owner
- `TimelineViewModel` is the absolute central source of truth for Project state (`_uiState.project`), playback (`isPlaying`), and playhead (`_playheadFrame`).
- `ColorAdjustmentViewModel` delegates to `TimelineViewModel`.

## 9. Current Preview Engine
- **Active Engine:** `MEDIA3_FALLBACK` (Media3PreviewPlayer) inside Compose.
- **Fallback:** `StillFramePreviewEngine`
- `TimelinePreviewController` configures the engine using `PreviewEngineFactory`.

## 10. Current Timeline Playhead State Source
- Extracted out of `TimelineUiState` data class and is now tracked directly via its own `StateFlow`:
  `val playheadFrame: StateFlow<Long> = _playheadFrame.asStateFlow()` in `TimelineViewModel`.

## 11. Playhead State Synchronization
- **Yes.** The Timeline UI, Viewport, Scopes, and Color UI all now observe `timelineViewModel.playheadFrame.collectAsState()`, decoupled from full project structure changes. This prevents the UI from resetting animations or tearing when only the playhead changes.

## 12. Color Slider Integration
- Color sliders in `ColorPanel` update the **project state**. As sliders are dragged, changes are emitted upwards via `onStackChanged` to `updateClipAdjustments` inside `TimelineViewModel`, modifying the global clip state inside the Track.

## 13. C++ / NDK Configuration
- **Configured:** Yes, CMakeLists.txt is present and configured, building successfully as part of `configureCMakeDebug` and `buildCMakeDebug`.

## 14. Native C++ Execution
- Native C++ functions are actually declared and mapped: JNI bridges like `NativePlayerBridge`, `NativeTransformEngine`, and `MotionBlurEngine` possess `external fun` bindings.

## 15. Current Build Status
- **Status:** Build executes and succeeds. No compilation errors.

### Key Findings & Observations

#### What is Working
- Build is passing!
- The single source of truth (`playheadFrame`) is correctly observed globally; the `TimelineViewModel` acts correctly as the app's central dispatcher reducing local state fragmentation.
- JNI definitions match with C++ and Gradle compilation is hooked correctly.

#### What is Broken / Needs Review
- Scrutinizing the native bridge: VLC libraries (`Class.forName("org.videolan.libvlc.LibVLC")`) are failing reflection gracefully falling back to `Media3`. This implies standard ExoPlayer is handling rendering, likely ignoring standard transform C++ engine unless we explicitly bridge the still-frame paths or `TransformCompositor`.
- Transform keys exist but rely entirely on `NativeTransformEngine` which has been bound but full frame accurate scrubbing capability of C++ in the fallback view has a known synchronization overhead via JNI when fetching generated byte buffers manually.

#### Files To Modify
- `ChromaProApp.kt` & Layout framework files if major layout refactoring is occurring.

#### Files Not To Touch (Yet)
- Any C++ file or `CMakeLists.txt`
- Core project model data structures (`TimelineProject`, `TimelineClip`).
- Gradle configurations (unless integrating a verified library). 

#### UI Layout Problems Found
- No massive constraints right now besides generic overlapping in dense panes when the `WindowSizeClass` changes or under multi-panes where we render graph editors inside sidebars. Need to check if tablets / horizontal layouts get proper canonical representations.

#### Playback & Color Integration Problems Found
- With the fallback mechanism, `Media3` natively doesn't natively apply our GLSL color LUTs effectively. NDK frame buffering is utilized via the Compose `canvas` but standard `ExoPlayer/Media3` uses standard `SurfaceView/TextureView` intercept that bypasses the C++ grade engine entirely for playback. Still frames fetch `StillFrameFallback` which correctly invokes grades on single `drawImage` calls, creating a discrepancy between play and pause visual states.
